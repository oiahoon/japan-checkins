# 私有缩略图与前台优先读取 · 2026-10-18

## 地图资料为前台照片让路 · 2026-10-19

日本细边界改为按当前县分片，定位建议仅请求该日本县，作品只请求筛选照片所在县；不再读取整份 4.25MB 文件。基础地图 / 目录（最多两路）和日中细边界（一路）在可见照片、查看器或导出大图读取期间暂停 / 中止，完成后自动恢复；后台拼图照片不阻塞边界以避免依赖互锁。暂停不算网络超时，地区离开会取消该消费者。没有改变原图、缩略图尺寸、私人缓存边界、照片信息或确认规则。详细契约见 [GEOGRAPHY](GEOGRAPHY.md)，本节优先于下文历史“日本分片待优化”描述。

## 线上旧图补生成与实际数据复测 · 2026-10-19

经用户明确授权，本实例 private 数据仓库已补生成 9 张可访问照片的缩略图；回收的照片或所属记录已回收的照片保持原状。仅新增缩略图文件与 thumbnailSha，逐文件 SHA-256 和去除该可选字段后的完整索引比较通过：原图、已有地点 / 日期 / 笔记、确认状态、旅行记录与其余文件不变。非强推提交后，从远端回读索引完全匹配；重复补生成产生 0 修改，仓库仍为 private。没有恢复回收数据、修改分享权限或把私人内容写入公开源码。

这批 9 张展示 JPEG 合计 6,081,406 bytes，对应缩略图 697,131 bytes，减少 88.5%；这是本实例结果，不是所有照片的固定压缩率。派生图比例、768px 上限、Git blob 校验及 EXIF / XMP / ICC 移除验证通过。

正式站密码登录后，390px 照片库实际读取 768px 缩略图，已有信息仍正确；大图保持 1600px。另以同一 Next.js 优化构建、真实私仓读取和临时本机认证，在仅回环的只读中继下测试全局 48KiB/s、每响应至少 400ms；中继拒绝所有数据写入，不修改生产认证。这里不是直接给生产域名做浏览器网络仿真，也不是物理 iPhone / Safari。私有截图和日志只保存在受限临时目录，不提交到公开 Git。

发现并修复的弱网预算问题：公开资料请求标记 low 优先级，超时从 15 秒调至 45 秒，避免正常慢传输误报失败；进阶版展示大图读取从 30 秒延至 90 秒，缩略图仍为 30 秒。旧逻辑打开任意照片编辑器都会拉取约 4.25MB 日本市区边界；现在仅在日本地图细层 / 拼图、旧版日本地点确认步骤或尚未应用的日本 GPS 提议确实需要时加载。中国照片、已填地区照片、仅选择上传文件不再触发这份数据，原有已填信息不改。请求仍可随关闭 / 离屏立即取消，前台抢占和权限检查不变。足迹导出的独立 15 秒单图 / 45 秒总预算未变，基础版 GitHub API 单次 / 整体期限也未改。

最终完整响应复测：大图 645,951 bytes 在 30.6 秒成功显示 1600×1200；地点目录 933,736 bytes 在 37.9 秒完整就绪，公开资料无超时、没有下载无关日本细边界。日志确认前台请求暂停缩略图，成功后恢复。390px 下照片 / 时间线切换、地图缩放拖拽、布局和 console 检查通过。脚本与部分页面资源已有浏览器缓存，中继对收到的请求移除 Range / 条件缓存并限速完整响应；这不是冷启动测速。178 tests 与两套构建、静态隐私扫描通过，发布证据见 [PROGRESS](PROGRESS.md)本轮记录。没有冷启动 LCP / INP / FPS、低端 CPU、丢包或所有大图库已达标的结论；地图全部行政区细边界的分片仍为后续优化。

## 已实现

照片库、时间线、记录卡片及地图照片拼图使用独立缩略图；编辑预览、照片查看器、足迹作品导出继续读取已有的清晰展示 JPEG。展示 JPEG 是原有上传 / 导入流程生成的最长边 1600px 图片，并非相机 RAW 原文件。本轮不降低它的分辨率、不重新压缩已有大图。

缩略图最长边 768px，保持比例、不裁切、不放大小图，JPEG quality 82（超过 512KiB 时尝试 74，仍过大则失败）。Sharp 转 sRGB 后输出，并再次移除 JPEG APP / COM 元数据。它不携带 GPS、拍摄信息或相机 EXIF；索引内已有的 metadata / proposal 保留原有权限和确认规则。

- 网页上传：服务端生成大图对应的缩略图，两文件和索引通过同一次 Git 树提交关联；相同上传 ID / digest 重试保持幂等。失败不提交半条照片记录。
- 私仓 Git 导入：转换照片时同步生成；正常导入也可补齐当前 manifest 中最多 30 张旧照片的缩略图。
- 可选字段 `thumbnailSha` 加入原有 version 1 索引，无数据库迁移。派生文件位于同一私有数据仓库 `travel/thumbnails/ID.jpg`，展示大图仍为 `travel/photos/ID.jpg`。
- 旧照片在进阶版请求缩略图时可按需生成响应，不写回数据仓库；基础版没有服务器处理能力，未补生成时回退已有大图。不是部署时把私人照片复制进公开构建。

## 优先级与取消

浏览器统一管理认证照片读取和页内 Blob URL。屏幕内列表为 visible，地图拼图为 background，编辑大图 / 查看器 / 导出为 foreground。总上限 3 路、被动读取最多 2 路。出现前台请求时暂停正在传输的被动请求，前台完成后恢复；暂停不会变成列表报错。相同源共用底层请求，单个组件取消不会误伤仍在读取它的查看器。

列表观察区为实际可见范围（0px 预取），滚动离屏或隐藏页面会取消该消费者的排队 / 在途读取；没有消费者时真正中止底层请求。旧版 160px 预取和仅基础版 3 路队列已由本方案替代。页内成功结果仍复用；失败可原位重试。地图拼图仍有 100 张 / 2 worker 的现有边界。

缓存只在当前页面内存中，基础版断开连接清除并撤销 Blob URL，进阶版退出为完整导航。没有 localStorage / IndexedDB 照片缓存、公共 CDN 或服务端跨用户照片缓存。当前没有有界 LRU，长时间浏览大图库仍需后续内存验收。

## 权限与删除

`/api/photos/ID?variant=thumbnail` 与大图使用相同服务端认证；每次底层读取核对 private 仓库、owner、行状态、所属记录回收状态。公开投影仍只允许显式发布照片。响应保持 private/no-store、nosniff 与 Vary Cookie，不暴露 Git blob SHA。基础版同样通过 Contents 只读授权访问自己的私仓，不能写入。

草稿彻底移除时同时移除当前树的大图和已有缩略图路径；软删除 / 恢复的权限门禁同时作用于两种版本。Git 历史保留的边界不变。本轮未改写现有生产私仓、未批量迁移真实照片，也未改变分享设置。

## 旧照片补生成（部署者主动操作）

先按 [升级与备份](UPGRADING.md)备份自己的私有数据仓库。源码更新后，在源码目录执行：

```sh
npm run thumbnails:git -- --repository-root "/path/to/your-private-data" --repository YOUR_ACCOUNT/my-travel-data
```

需 Node >=22.18、已完成 npm ci，并使用已认证的 gh 或已有 GITHUB_TOKEN / GH_TOKEN。命令核对 Git remote 与 GitHub 实际 private 属性，不接受公开数据仓库。只处理缺少缩略图的有效照片，每次最多 30 张；校验展示 JPEG 的 Git blob SHA、文件大小与路径，不需要 inbox 原文件。重复运行补齐后不再产生修改，不改变照片说明、EXIF 提议、确认、旅行记录或大图。索引最后写入；这个命令本身不创建 Git 提交。

随后在自己的数据仓库审阅新增 `travel/thumbnails/` 与 `travel/index.json`，确认无其他未提交数据后，再自行 commit + push。数据分支在此期间不要同时进行网页写入；有远端更新先 pull 并核对，不强推。

也可以更新私仓内复制的 [导入工作流](../deploy/github-import.yml)后，在其 Actions → Import private travel photos → Run workflow 勾选 `thumbnails_only`。每次最多补 30 张并在私仓提交；超过 30 张可再次运行。模板复制不会随源码自动更新，按升级指南保留自己的定制。切勿将此工作流装在公开数据仓库；源码仓库的 Pages / Vercel 构建不读取任何私人照片。

# 可选批量任务方案 · 队列尚未实现

2026-10-18：可选Upstash Redis写入租约与登录限流适配已实现，代码默认关闭；本部署已获批共享Free库并配置Production连接，运行时启用及云端验收仍待重新发布；见 [KV配置与边界](KV.md)。本节的跨请求批次、状态和消费者仍为计划。

当前进阶版逐张上传独立私有照片，用户明确保存信息；每次写入是原子Git提交，现有批次上限不变。当前没有必需Redis依赖、后台队列、自动打包上传或异步完成承诺。

考虑的后续流程是：认证主人创建batch → 每张照片本机解析 / 转换、独立幂等上传 → 暂存处理后的Git blob SHA与元数据 → 明确完成批次 → 一次提交索引与全部照片引用。照片独立记录与逐张确认仍保留，批量提交不等于自动合并旅程。浏览器显示待上传 / 暂存 / 提交中 / 已保存，**只有Git ref提交成功才显示已保存**。

Redis可选用于owner范围的任务状态、幂等键、进度、短期锁和失败重试，不存放原图、访问令牌或永久旅行记录。任务只记录受验证的照片ID / blob SHA；索引与Git提交仍是事实来源。TTL和锁过期不能丢失已接受的照片；重试沿用ID并核实已有提交，崩溃后可恢复，不永久依赖某个实例的内存。提交冲突要重新读取最新head合并，不强推。

跨请求批次需要服务端持久状态和实际消费者；仅加Redis客户端或仅在Vercel请求结束后启动Promise都不算队列实现。选定托管供应商、函数/消费者机制、批次容量、blob清理策略后，再验收并开启。多实例并发、断网 / 丢响应、owner隔离、超时、取消、重复完成、过期和配额耗尽都应测试。避免把Redis当基础部署门槛。

GitHub基础版无需这套队列：用户通过Git提交输入，私仓Actions在有界任务中生成数据并一次提交。工作流失败不发布部分索引；同时写入导致非强推失败时重新运行读取最新分支。Git/Actions的日志与原始inbox仍应保持私有。
